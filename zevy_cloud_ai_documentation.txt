ZEVY CLOUD – SYSTEM ARCHITECTURE BLUEPRINT
Last Updated: February 2026

============================================================
1. PRODUCT AND PLATFORM SCOPE
============================================================

Zevy Cloud is the broader platform around Zevy AI. It includes:
- The Zevy AI conversational engine (Astra + Vyra + Axiom Core).
- The web application (Next.js 14).
- Authentication, storage, and analytics (Supabase).
- External integrations (Groq, web search APIs, time APIs, etc.).

This document focuses on:
- Cloud-side architecture (how the backend is structured).
- Security and safety boundaries.
- Data flows between frontend, backend, third-party APIs, and Supabase.


============================================================
2. ARCHITECTURE LAYERS
============================================================

2.1 Client Layer (Browser + Next.js)
------------------------------------

Technologies:
- Next.js 14 app directory.
- React components with Tailwind/CSS utility classes.
- LocalStorage for guest persistence.

Responsibilities:
- Render chat UI and settings UI.
- Manage:
  - Current model (Astra / Vyra).
  - Vector / Web Search toggle.
  - Mindset and trait selection.
  - Theme (dark/light).
- Prepare and send requests to /api/chat:
  - message and chat_history
  - modelType (astra | vyra)
  - searchEnabled flag
  - mindset
  - beastMode flag
  - documents array for uploaded files.

Security considerations:
- No API keys are embedded in client-visible code.
- Sensitive configuration is provided only via environment variables on the server.


2.2 Edge / API Layer (Next.js Route Handlers)
---------------------------------------------

Primary route: app/api/chat/route.ts

Key responsibilities:
- Entry point for all chat requests.
- Authentication via Supabase session (for logged-in users).
- Guest mode handling (anonymous usage with local limits).
- Content moderation and safety checks.
- Routing between Astra and Vyra reasoning paths.
- Orchestrating Groq Compound calls for web research.
- Recording usage statistics and enforcing per-model usage caps.

This layer is effectively the “controller” for the AI:
- It decides *whether* a request is allowed.
- It decides *how* to answer (Astra vs Vyra, with or without search).
- It decides *how much* external knowledge to load.

SYSTEM_PROMPT(currentTime, timezone, searchEnabled, mindset, isBeastMode)
- Generated per-request on the server.
- Encodes:
  - Zevy’s persona as Axiom Core (brutal truth, architect tone, no fluff).
  - Search status (ON/OFF) and instructions on how to treat research context.
  - Mindset-specific behaviour (Philosopher, Strategist, Storyteller, etc.).
  - Beast Mode behaviour (more intense, philosophy-heavy, higher ego) while keeping safety rules.
- This server-side system prompt is used for:
  - Astra responses.
  - Vyra debate steps.
  - Groq Compound analysis prompts.


2.3 Model Provider Layer (Groq + Others)
----------------------------------------

Groq is the primary LLM runtime provider.

Used models (typical, exact IDs configurable via environment):
- Vyra:
  - Kimi K2 (moonshot-like) – “Kairo”.
  - Qwen 32B – “Logos”.
- Astra:
  - Llama-based scout model for speed.
  - Llama-based maverick model for deeper analysis.
- Guard:
  - Llama Guard 4-12b for safety classification.
- Compound:
  - One or more Groq-hosted models for analyzing aggregated web/news/Wikipedia content.

The backend never exposes model IDs directly to the user. It only exposes:
- User-visible model names: “Astra” and “Vyra”.
- High-level descriptions: “fast research” vs “deep debate”.


2.4 Data Layer (Supabase + LocalStorage)
----------------------------------------

Supabase:
- Postgres database accessible from the Next.js application.
- Used for:
  - User accounts and sessions.
  - Conversation history (per user, per chat).
  - Usage tracking for Astra and Vyra.
  - Saved traits / mindsets / preferences.

LocalStorage (frontend):
- Used for:
  - Guest user histories (keyed per conversation).
  - Trait and mindset for guest usage.

No raw API keys or secrets are stored in Supabase or LocalStorage:
- API keys are in environment variables on the server only.
- User-level data is limited to conversation content and profile-level settings.


============================================================
3. END-TO-END REQUEST SEQUENCE
============================================================

Step 1: User Action
-------------------
- User selects model (Astra/Vyra), toggles Vector ON/OFF, picks a mindset, and types a message.
- Optional: user attaches documents to the chat.

Step 2: Frontend Packaging
--------------------------
- app/page.tsx prepares:
  - message
  - chat_history (from local state)
  - model
  - searchEnabled / webSearch
  - mindset
  - beastMode
  - processed documents (already converted to text).
- It ensures all documents are fully read before sending:
  - If uploadProgress is non-empty, sending is disabled and a notification is shown.

Step 3: Backend Entry (POST /api/chat)
--------------------------------------
- The route:
  - Parses the JSON body.
  - Derives effective searchEnabled from multiple flags.
  - Normalizes modelType to 'astra' or 'vyra'.
  - Extracts documents and builds documentsContext.
  - Attaches an “Attached documents” user message into the chat history.

Step 4: Moderation
------------------
- isSafe(prompt) is called:
  - Builds a detailed moderation prompt for Llama Guard.
  - Accounts for:
    - Illegal content (crime, serious fraud).
    - Hate speech, harassment, extreme violence.
    - Self-harm, suicide, explicit sexual content.
    - Private information and malicious code.
  - Adds relaxations:
    - Lyrics / music queries.
    - Figurative language (“this killed me”, “dying of laughter”).
    - Legal / moral / hypothetical dilemmas.
    - Descriptive crime content (stories, cases, files, victims) without “how to”.
- If unsafe:
  - Returns a 400 response with an explanation.
- If safe:
  - Continues to main logic.

Optional: isPromptSafe(prompt, userModel)
- Secondary check that uses a more compact moderation prompt.


Step 5: Router Logic
--------------------

Case A: Owner commands
- If the user is recognized as creator/owner and the message matches command patterns:
  - Special routines for diagnostics, admin, or internal debugging may run.

Case B: Normal user, Astra
- If modelType is 'astra':
  - If Vector is ON:
    - Calls gatherKnowledge() which uses Groq Compound (browseAndAnalyze).
    - Produces a knowledgeContext string.
    - Builds a Groq call with:
      - SYSTEM_PROMPT(...) as system content.
      - User message that includes:
        - knowledgeContext.
        - user’s resolved question.
        - previous conversation.
  - If Vector is OFF:
    - Calls Groq directly with SYSTEM_PROMPT as system, plus the question and history.

Case C: Normal user, Vyra
- If modelType is 'vyra':
  - Takes a more complex pipeline:
    1. Knowledge gathering:
       - Uses Groq Compound with a Vyra target model and forceSearch when Vector is ON.
       - Aggregates web, news, and Wikipedia context.
    2. Internal analyses:
       - Kairo analysis of the topic.
       - Logos analysis of the topic.
    3. Cross-debate:
       - Kairo challenges Logos.
       - Logos defends and refines.
    4. Final synthesis:
       - A dedicated prompt that:
         - Sees all prior internal texts.
         - Is instructed to answer as Zevy (Axiom Core) in one clean voice.
         - Prioritizes brutal truth with a respectful but blunt tone.


Step 6: Usage Tracking and Limits
---------------------------------
- Before finalizing the answer, the route:
  - Checks current usage from Supabase (getUserUsage).
  - If limits are exceeded:
    - Returns a message indicating limit reached.
    - Skips calling Groq to avoid unnecessary cost.
  - Otherwise:
    - Increments usage counters.
    - Stores conversation updates in Supabase.


============================================================
4. CONFIGURATION AND ENVIRONMENT
============================================================

Configuration relies on environment variables (names only, no secrets in this document):
- GROQ_API_KEY_*: credentials for Groq model access.
- GOOGLE_SEARCH_API_KEY / SEARCH_ENGINE_ID: web search integration.
- SUPABASE_URL / SUPABASE_ANON_KEY / service keys: for database and authentication.
- Optional other open-data API keys (NASA, etc.) used by Groq Compound.

Security posture:
- Keys are only loaded on the server side.
- No secret is sent to the client.
- Only aggregate data (e.g., usage counts and messages) is stored in Supabase.


============================================================
5. PERSONA, MINDSET, AND BEAST MODE
============================================================

Persona: Axiom Core
- The global persona is not a separate model; it is the system prompt layer layered on top of Astra, Vyra, and Groq Compound.
- It enforces:
  - Single-voice behaviour: one consistent mind, not multiple characters.
  - Brutal truth and objective logic.
  - Architect-style tone: foundational, blunt, and focused.
  - No fake friendliness; no repeated small-talk greetings.

Mindset:
- The user can choose a mindset such as:
  - Balanced (default)
  - Philosopher
  - Strategist
  - Storyteller
  - Others (as defined in code)
- The backend passes this mindset into SYSTEM_PROMPT as extra guidance:
  - Philosopher: emphasise ethics, meaning, and long-term consequences.
  - Strategist: emphasise trade-offs, plans, and decision frameworks.
  - Storyteller: emphasise examples and scenarios, without turning graphic.

Beast Mode:
- When Beast Mode is active:
  - The persona becomes more intense, philosophical, and high-ego.
  - It uses sharper metaphors and a more confrontational analytic style.
  - It still respects safety rules and does not encourage real-world harm.


============================================================
6. FAILURE MODES AND FALLBACKS
============================================================

Groq / Compound failures:
- If browseAndAnalyze throws:
  - The backend logs an error.
  - A backup message is constructed telling the model:
    - Web research failed.
    - Use only internal knowledge.
    - Give a best-effort answer while acknowledging possible inaccuracy.

Moderation failures:
- If Llama Guard or moderation logic fails unexpectedly:
  - The system may either:
    - Default to allowing the prompt (to avoid blocking the entire chat), or
    - Return a generic safe error message, depending on the failure type.

Search failures:
- If external web search or news APIs time out or error:
  - Groq Compound falls back to reduced sources or partial knowledge.
  - The model is instructed to answer cautiously and avoid pretending to have fresh data.
